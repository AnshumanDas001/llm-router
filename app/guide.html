Documentation

ThriftLLM classifies each request, routes it to the cheapest model tier likely to handle it, and verifies the answer before trusting it — escalating only when needed. This page covers both the web app and the API.

Introduction

Most LLM traffic doesn't need your most expensive model. ThriftLLM sits in front of three tiers — cheap, mid, frontier — and for each request:

  1. Classifies difficulty using embedding similarity against a labeled reference set (no model call, instant)
  2. Generates an answer with the cheapest tier likely to succeed
  3. Verifies the answer — a real check for the cheapest tier, a free structural check for the rest
  4. Escalates to the next tier only if verification fails

You can use your own models end to end: we never store your upstream provider keys, only the routing decisions and derived cost/quality numbers.

i

Two ways to use this: the chat app for interactive use, or the API for programmatic integration — covered below.

Authentication

API requests authenticate with a key you create in Sessions or Settings, sent as a bearer token:

Authorization: Bearer rtr_your_key_here

Each key is its own session — every call made with it groups together in Sessions for cost/usage tracking. Create a separate key per integration if you want them tracked separately.

!

Keys are shown once, at creation. We store only a SHA-256 hash, the same way Stripe and GitHub hash their own issued tokens — there's no way to retrieve a lost key, only revoke and recreate.

Quickstart

Three steps: create a key, calibrate your models (or skip this to use our built-in tiers), then route a request.

curl -X POST https://your-router-host/api/v1/route \
  -H "Authorization: Bearer rtr_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{
    "messages": [{"role": "user", "content": "What is the capital of France?"}],
    "tier_api_keys": {"cheap": "your-groq-key", "frontier": "your-gemini-key"}
  }'
import requests

resp = requests.post(
    "https://your-router-host/api/v1/route",
    headers={"Authorization": "Bearer rtr_your_key_here"},
    json={
        "messages": [{"role": "user", "content": "What is the capital of France?"}],
        "tier_api_keys": {"cheap": "your-groq-key", "frontier": "your-gemini-key"},
    },
)
data = resp.json()
print(data["choices"][0]["message"]["content"])
print(data["_router"])  # tier used, cost, escalated, etc.
const resp = await fetch("https://your-router-host/api/v1/route", {
  method: "POST",
  headers: {
    "Authorization": "Bearer rtr_your_key_here",
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    messages: [{ role: "user", content: "What is the capital of France?" }],
    tier_api_keys: { cheap: "your-groq-key", frontier: "your-gemini-key" },
  }),
});
const data = await resp.json();
console.log(data.choices[0].message.content);
console.log(data._router);

Your upstream provider keys (tier_api_keys) are used only for this one request and never written to disk.

Tiers

Three named tiers, each mapped to a real model. Our defaults, or bring your own via calibration:

TierRoleOur default
cheapHandles most easy/medium traffic, free or near-freeollama/llama3.2:3b
midHandles hard traffic directly; nearly frontier-quality at a fraction of the costgroq/openai/gpt-oss-20b
frontierLast resort — genuinely ambiguous tasks and rare escalationsgemini/gemini-3.5-flash-lite

You don't need all three configured — the cascade works over whichever subset you provide.

Classifier & cascade

The classifier compares your query's embedding against a labeled reference set (61+ hand-scored examples, growing via an active-learning loop from real escalations) using 1-nearest-neighbor, then combines that with cheap text heuristics (query length, code/multi-step keywords) to guess a starting tier. This costs nothing — no model call.

From there: generate with the guessed tier, verify, escalate to the next tier only on failure. The cascade never revisits a tier once it's been tried and failed.

Verification

Two strategies, chosen by position in the tier sequence, not the literal tier name:

  • The cheapest configured tier gets a real, paid LLM-judge check by the next tier up — asking whether the response addresses every part of the request and stays coherent.
  • Every later tier gets a free structural check only (non-empty, not a refusal). Verification cost scales with response length, and later tiers' failure rates are low enough that a full judge call there isn't worth the cost.
  • The last tier in the sequence is never checked — there's nothing left to escalate to.
i

If a tier is temporarily rate limited, the cascade skips it and moves to the next one rather than failing the whole request.

Calibration — via the web UI

In Settings, enter a model string and your provider key per tier, then click Run calibration. This runs ~24 objectively-scoreable queries (math, logic, code-tracing — no LLM judge needed) against your model live, using your key once, transiently. Only the resulting quality/cost/latency numbers are stored.

The query set is stratified by difficulty, so each tier gets a separate easy / medium / hard score rather than one blended average. That distinction is the point: a model that aces easy and medium but collapses on hard still posts a respectable overall number, and routing needs to know the difference.

What calibration decides

Those per-difficulty scores produce your routing map — for each difficulty, traffic starts at the cheapest configured tier that scored at least 80% on that difficulty, and escalates from there only if a check fails. Settings shows the resulting map after every run.

Without calibration, a BYOM account would route by our defaults, which encode our measurements of our models — wrong in both directions for someone else's stack. Calibrate, and the map is derived from your own numbers. Re-calibrating with different models re-derives it.

i

A tier whose calibration calls all fail (bad model string or key) is reported in warnings and not saved, so a broken model can't silently become a routing target.

Calibration — via the API

The same calibration, without touching the browser. Calibration is keyed by model, so you measure a model once and can then slot it into any tier of any session without re-measuring. Authenticate with your API key instead of a login session:

curl -X POST https://your-router-host/api/v1/calibrate \
  -H "Authorization: Bearer rtr_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{
    "model_name": "groq/llama-3.1-8b-instant",
    "api_key": "your-groq-key"
  }'
import requests

resp = requests.post(
    "https://your-router-host/api/v1/calibrate",
    headers={"Authorization": "Bearer rtr_your_key_here"},
    json={"model_name": "groq/llama-3.1-8b-instant", "api_key": "your-groq-key"},
)
print(resp.json())  # {"model_name": ..., "stats": {...}, "warnings": [...]}

The model must already be connected to your account (Settings → Models & calibration, or the Providers UI). api_key is optional — omit it if you saved that provider's key.

  • stats.quality_by_difficulty — easy/medium/hard scores, the input to routing. null for a difficulty whose queries all failed.
  • stats.n_rate_limited — queries lost to provider throttling, reported separately from real failures.
  • warnings — unmeasured difficulties and partial runs.
i

A model whose calibration calls all fail returns an error and is not saved, so a broken model string can't silently become a routing target. The message distinguishes a bad model string from a provider rate limit.

The full programmatic flow

Define your models in your own code → connect them once → calibrate each → route every request against whichever three you want for that call:

HEADERS = {"Authorization": "Bearer rtr_your_key_here"}
MODELS = {
    "cheap": "groq/llama-3.1-8b-instant",
    "mid": "openai/gpt-4o-mini",
    "frontier": "openai/gpt-4o",
}

# one-time: measure each model
for model in MODELS.values():
    requests.post(f"{HOST}/api/v1/calibrate", headers=HEADERS,
                  json={"model_name": model, "api_key": PROVIDER_KEY})

# every request thereafter
resp = requests.post(f"{HOST}/api/v1/route", headers=HEADERS, json={
    "messages": [{"role": "user", "content": "What is 2+2?"}],
    "models": MODELS,
    "tier_api_keys": {"cheap": GROQ_KEY, "mid": OPENAI_KEY, "frontier": OPENAI_KEY},
})

tier_api_keys is only needed for tiers whose provider key you chose not to save; saved keys are used automatically.

API reference

POST/api/v1/route

Routes one chat completion through the cascade using your configured models.

Request body

FieldTypeDescription
messagesarrayOpenAI-style {role, content} messages
tier_api_keysobjectYour upstream keys per tier, used transiently, never stored

Response

OpenAI-shaped chat completion, plus a _router block:

{
  "choices": [{"message": {"role": "assistant", "content": "..."}}],
  "usage": {"prompt_tokens": 12, "completion_tokens": 8, "total_tokens": 20},
  "_router": {
    "difficulty": "easy",
    "initial_tier": "cheap",
    "final_tier": "cheap",
    "escalated": false,
    "escalation_reasons": [],
    "cost": 0.00003,
    "baseline_cost": 0.00097,
    "latency_ms": 812.4
  }
}
