ThriftLLM internals

A cost-routing cascade for LLM traffic: classify each request, send it to the cheapest model that can plausibly handle it, check the answer, and escalate only when the check fails. This document describes every mechanism, the measurements behind each decision, and the things that were tried and abandoned.

4,601 lines of Python · 4,348 lines of templates and styles · 2,454 lines of eval tooling · 31 tests · 17 tables · 49 endpoints

1The problem, and the one that matters

Most traffic to a language model does not need the most expensive model available. The naive saving is obvious: route easy work to a small model. The hard part is that the obvious baseline is not "the frontier model" — it is "one good mid-tier model for everything." A cascade that beats frontier-only but ties mid-only has bought nothing.

That distinction drove most of this project's design. The first built-in stack (llama3.2:3b locally → gpt-oss-20b → gemini-3.5-flash) came out at $0.0204 against $0.0205 for mid-only over 116 queries — a tie — and the breakdown said why:

  • 80% of spend was hard questions, which the 3B model could not do, so they went to mid either way.
  • On the rest, verification cost what it saved: 63% of cheap answers paid a judge call, 28% escalated and paid a full mid answer, and 0.63 × judge + 0.28 × escalation came to mid's own price. With the judge being the mid model, that is a ratio — it holds at any price level, so simply picking a pricier mid would not have fixed it.

Two changes turned the tie into a win, and they are the heart of the current design:

  1. A judge far cheaper than the answer it protects. A verdict reads ~450 tokens and writes one word. gpt-oss-20b does that for $0.00004 and catches 94% of wrong cheap answers. Tying the judge to the tier above makes verification scale with that tier's price; decoupling it is what makes the cascade pay.
  2. A cheap tier that clears the quality floor on more bands, so the paid model only sees what the cheap one actually gets wrong.
Result

Over the same 116 queries: $0.132 against $0.225–0.360 for mid-only and $0.735 for frontier-only, with 76/76 objectively-graded answers correct. 41–63% under mid-only depending on which baseline estimate you take; the project quotes the conservative one.

2Request lifecycle

Every request — chat UI, demo, or API — goes through the same path in app/routing/cascade.py. Nothing about it requires an LLM to make the routing decision.

flowchart TD
    Q[Prompt] --> C["Classify difficulty
MiniLM-L6 · expert gate + weighted k=5 · ~7ms · no model call"]
    C --> P["Pick start tier
min expected total cost, subject to a 0.80 quality floor"]
    P --> G[Generate at that tier]
    G --> S{"Learned scorer
P(correct) from token logprobs · free"}
    S -->|"P ≥ 0.95"| OUT[Ship the answer]
    S -->|otherwise| J{"LLM judge
small model · $0.00004"}
    J -->|passes| OUT
    J -->|fails| E[Escalate one tier]
    E --> G2[Generate at next tier]
    G2 --> ST{Structural check
non-empty, not a refusal}
    ST -->|passes| OUT
    ST -->|fails| F[Final tier · never checked]
    F --> OUT

Three invariants hold throughout:

  • Only the cheapest configured tier gets a real judge call. Later tiers fail rarely and their answers are long; judging every tier once accounted for 82% of total spend.
  • The last tier in a sequence is never verified. There is nothing left to escalate to, so a verdict cannot change the outcome.
  • A tier is never revisited once tried and failed.

3Difficulty classifier

app/routing/classifier.py — 187 lines, no model call, about 7ms.

The prompt is encoded with all-MiniLM-L6-v2 (22M parameters, pinned to CPU) and compared by cosine similarity against 176 labelled reference questions: 116 everyday ones (easy / medium / hard) and 60 AIME problems (expert). Two stages:

  1. Expert gate. If at least half the similarity weight among the 7 nearest neighbours belongs to expert questions, the prompt is expert.
  2. Otherwise, a similarity-weighted vote over the 5 nearest everyday neighbours: each contributes its similarity score to its own label, and the heaviest label wins.

Why a gate rather than a fourth label in the vote

A wrong expert pays for a thinking answer it didn't need, so the gate is tuned against those false positives. Leave-one-out over all 176 questions:

designAIME caughteveryday pulled to experteveryday exact
one k=5 vote over four labels53/6010/116—
no expert band at all——75/116
gate (k=7, share ≥ 0.5), then k=5 over everyday54/604/11672/116

The four false experts are maths questions such as "the smallest n with n! divisible by 1000". The frontier answers them correctly, at a higher price. python -m scripts.classifier.evaluate_loo prints the full confusion matrix.

Why k=5 and not 1-NN

It began as single-nearest-neighbour, on the theory that k-voting lets mediocre matches outvote one clearly-best match. Measured properly — leave-one-out across the 116 everyday queries, with today's overrides — that reasoning was wrong:

classifierexact labelover-routedunder-routed
1-nearest-neighbour55.2%2230
weighted k=5 vote64.7%2417
expert gate, then the k=5 vote62.1%2717

Over-routed = labelled harder than it is, and so possibly paid for a stronger tier than needed. Under-routed = labelled easier, which the verifier usually catches. All rows are counted the same way; an earlier version of this table mixed counting methods.

Single-neighbour is fragile here because the reference set is 52% hard, so one spurious topical match drags a query straight to the mid tier. Summing similarity over five neighbours dilutes that.

Structural overrides

Embedding similarity measures topic, not difficulty. "What's the worst case of quicksort" sits beside "explain why naive quicksort degrades to O(n²)" because both are about quicksort, though one is recall and the other is analysis. Four rules patch the worst of it:

conditioneffectrationale
> 25 words, or matches a multi-step keyword (explain why, step-by-step, compare, tradeoff, design…)at least mediumlength and explicit multi-part structure are real difficulty signals the embedding misses
contains code keywords and the vote said easyraise to mediumcode questions have a long tail the embedding under-rates
vote said hard, but it's ≤ 12 words, opens with an interrogative, and has no multi-step markercap at mediumshort recall questions matched on topic, not difficulty; medium still starts cheap, and the verifier is the safety net
no neighbour has positive similaritymediuma neutral default rather than a coin flip
Thread safety, learned the hard way

FastAPI runs sync endpoints in a threadpool, and /api/classify fires on every debounced keystroke — so it can land while a chat request is classifying. Two consequences, both load-bearing: the model is pinned to device="cpu" because sentence-transformers otherwise selects Apple's MPS backend, and concurrent encodes from two threads killed the whole process with an IOGPUMetalCommandBuffer assertion. And a single lock wraps both load and encode, so concurrent callers serialise rather than racing one model object.

4Expected-cost routing policy

app/routing/policy.py — 118 lines. Turns calibration numbers into a difficulty→tier map.

Before this existed, calibration was inert: it measured quality and then only displayed it, while every account routed by one hardcoded map. The policy applies two rules per difficulty band.

Rule 1 — a quality floor

A tier may only start a band if its measured quality on that band clears QUALITY_THRESHOLD = 0.80. Below that, too many answers are wrong for the verifier to be trusted to catch them all. The strongest configured tier is always a legal start, so a request always has somewhere to go.

Rule 2 — lowest expected total cost

Among tiers clearing the floor, pick the one minimising the cost of the whole path: generation, the judge call if this is the cheapest configured tier, and the failure-weighted cost of escalating. Solved back to front, since the last tier is trusted unconditionally:

Ei(d) = c(ti, d) + J·1[i=0] + (1 − Q(ti, d)) · Ei+1(d)
En(d) = c(tn, d)

tier(d) = argmini Ei(d)   over i where Q(ti,d) ≥ τ, or i = n

c = measured generation cost per band, Q = measured quality per band, J = cost of one verification, τ = 0.80. Per band, not overall, because a mid model's easy answers can cost 7× less than its mean.

The J term is what stops a cascade losing to its own mid tier. On a stack whose mid model is very cheap, the cheap tier's verdict costs about what mid's own short answer does, and a naive "cheapest first" rule routes into a loss. Pricing the path makes the policy route around a cheap tier that cannot pay for its verification, and to one that can.

The map is an output, not a setting. Fed the current stack's measurements it derives easy→cheap, medium→cheap, hard→cheap, expert→frontier; fed the old 3B stack's it derived hard→mid, because that model scored 0.73 on hard.

On expert, starting lower looks cheaper on paper, but neither cheap (0.00) nor mid (0.70) clears the floor, so the frontier starts. The arithmetic assumes failures get caught, and mid's answers only get a structural check; the floor is what stops its wrong 30% from shipping.

5Two-stage verification

app/routing/scorer.py (267 lines) and app/routing/verifier.py (131 lines).

The cheapest tier's answer passes through a learned gate, then — only if the gate is unsure — an LLM judge. Later tiers get a free structural check; the last tier gets nothing.

Stage 1 — the learned scorer (free)

This is FrugalGPT's idea (replace the LLM judge with a small learned model) corrected by measurement. A logistic regression reads signals the cheap model emits with every answer:

feature groupfeaturescost
token confidencemean_logprob, min_logprob, p10_logprob, frac_uncertain, head_logprob$0 — metadata on the answer already generated
distributionalmean_entropy, max_entropy over the top-5 alternatives per token$0
shapelog_tokens, truncated, is_easy/is_medium/is_hard$0
consistency (available, not shipped)consist_max, consist_mean, numeric_agree — versus a second sampleone extra cheap generation
self-check (available, not shipped)self_verify — P(YES) read off the logprobs of a one-token "is this correct?"one tiny cheap call

The trained model records which features it uses, and the cascade skips any call nothing depends on. The shipped scorer uses only the free twelve, so stage 1 makes no API call at all.

P(correct)actioncost
≥ 0.95ship the answer, no judge call$0
< 0.95ask the judge~$0.00004

Both thresholds are measured, and deliberately lopsided because the two mistakes are not symmetric. Accept at 0.95 is the highest band in which zero wrong answers slipped through held-out cross-validation (0 of 15; at 0.90, two would have). Reject ships disabled (threshold 0.0): in the low-confidence band most answers the scorer doubts are in fact correct — at P < 0.05, half of them — so escalating on the scorer's word alone buys a needless paid answer. The judge is better at that call, so it makes it.

Stage 2 — the LLM judge

A small, cheap model — not the tier above — is asked whether the response addresses every explicit part of the request and is coherent, and replies with one line: YES or NO: <reason>. Measured on 117 graded answers it catches 94% of wrong ones, against roughly half for the scorer. That gap is exactly why the scorer gates the judge rather than replacing it.

Two details that cost real money to find. Reasoning models bill hidden thinking tokens as output: gpt-oss-20b spent $0.00016 per verdict against $0.00005 nominal until reasoning_effort was set, which cut a test verdict from 108 output tokens to 22 with the same answer. And an empty verdict (a truncated reply) fails toward escalation rather than silently trusting an unreadable answer.

Stage 3 — structural check (later tiers)

Free, no model call: empty response, or a refusal pattern. Deliberately no minimum-length rule — an earlier 20-character threshold flagged a one-word answer like "Neutral" to a classification query as suspiciously short and triggered a real, costly escalation for no quality reason.

When the gate is worth running

This depends entirely on what a verdict costs relative to the answer it protects. On the current stack a $0.00004 judge guards a $0.002 answer, so verification is 2% of the bill and the gate trims about 5% of that — real but small. Point the judge at the tier above, as the first stack did, and a verdict costs about what the next answer would; there the same code is the difference between a cascade that pays for itself and one that ties its own mid tier.

6Escalation and failure handling

Escalation moves one tier up the configured sequence. Several failure modes are handled explicitly, each discovered in production:

conditionbehaviourwhy
tier rate-limited, unreachable, or has no valid credentialsskip it, try the nexta quota or a local model that isn't running shouldn't fail the request; auth is included because a deploy can legitimately leave a tier's key unset
the verifier itself is rate-limitedfail open — trust the answerthe verifier being unavailable is not evidence the answer is wrong
cheap provider returns no logprobsfall back to the judge for that callthe gate needs them; the judge doesn't
every tier unavailableAllTiersUnavailable → 503only after exhausting the sequence

Streaming

Streaming and verify-then-escalate are in tension: a tier's answer can't be judged until it is complete, but waiting for completion is what streaming exists to avoid. Rather than withhold every token until the verdict is in, run_cascade_stream streams optimistically and emits an escalated event if the check then fails — the client drops what it showed and takes the next tier's answer. Escalation ran 26 of 116 in the measured run, so the common path streams cleanly and the uncommon path shows the router doing the thing it exists to do.

Events: routing → tier_start → token* → (escalated) → done | error. Streams ask for a final usage block (stream_options.include_usage), and cost is priced from it, hidden reasoning tokens included. Before that, a streamed answer was priced from its visible text at ~4 characters per token, which put a $0.19 thinking answer at a fraction of a cent. Providers that send no usage still fall back to that estimate.

Routing modes

Per chat and per API request: cascade as described, or direct, which skips the cheapest tier and starts one up. Because the paid judge only ever attaches to the cheapest configured tier, starting above it disables verification for free. direct is the right choice when the cheap tier is slow — a locally-hosted model, say — and latency matters more than cost.

Quality and cost are per easy / medium / hard / expert band. Cost is what the provider charged, hidden reasoning tokens included. The expert band comes from the AIME probe: ten problems for cheap and mid, and only mid's three misses for the frontier, so its own score is left blank. Three choices worth explaining

Mid and frontier are the same model, separated only by whether it may think. Mid runs reasoning_effort=minimal: at its default it spent 720 thinking tokens on a two-sentence answer — 94% of a $0.0069 bill — and gave the same answer for $0.0005 without. The frontier is the same model with thinking on. That two tiers share a model is the finding, not a shortcut: thinking-versus-not is the axis that actually predicted success.

The judge is a different, cheaper model than mid. This is the single decision that makes the cascade pay (§1).

Reasoning effort is per-stack configuration, not a constant. Values are provider-specific: Gemini needs minimal to stop thinking and ignores low; Groq's gpt-oss takes low/medium/high and rejects minimal outright.

Consequence of sharing a model

Mid and frontier have an identical per-token list price, so cost comparisons must come from calibration — which measures the reasoning tokens — rather than price × tokens. Priced naively the two look identical and the app's "saved vs frontier" counter reads near zero; estimate_frontier_cost therefore prefers the calibrated per-band figure ($0.0087 for a hard answer, against $0.0072 from the naive estimate).

8Calibration

app/evaluation/calibration.py (159 lines), scripts/calibration/calibrate_builtin.py.

Calibration runs objectively-scoreable questions against a model and scores each difficulty band separately. Those numbers are the only input to the routing policy, so their shape matters more than their precision.

Stratified, then interleaved

Stratified because a single blended average cannot answer the question routing needs — "does this model hold up on hard queries?" — since a model that aces easy and collapses on hard still posts a respectable mean.

Interleaved because running the bands in blocks put hard last, and a provider rate limit partway through wiped out the entire hard bucket — the one band the routing decision most depends on — while easy and medium looked perfect. Round-robin degrades every band evenly instead of silently losing one.

Sample sizes are asymmetric on purpose

The cheap tier is measured on all 76 auto-gradable queries; paid tiers get a stratified 24. The cheap tier's numbers decide what never reaches a paid model, and it is nearly free to measure. The asymmetry was earned: 8 questions per band once put a 3B model at 0.88 on hard where 76 said 0.73, and a hosted 8B at 1.00 where 120 samples said 0.74. Either would have routed hard questions to it on noise.

Other behaviours

  • Rate limits are retried once after 20s, then recorded as rate-limited rather than as a broken model — lumping them together made a throttled run look like a bad model string.
  • A built-in tier is measured with the parameters it actually runs with (reasoning effort, max_tokens, local api_base); BYOM models get provider defaults and the caller's key.
  • An empty answer scores as wrong, not as an error. A reasoning model that spends its whole budget thinking and returns nothing has failed to answer.
  • An unreachable tier is priced from list price at typical per-band token counts and flagged unmeasured, rather than aborting the run.
  • Results go to data/calibration/builtin.json, which is used only if its recorded model names still match the configured ones.
  • The built-in expert band is read from the AIME probe results rather than re-measured: a frontier AIME answer costs $0.13–0.29, so it is paid for once and kept (calibrate_builtin --expert-only). BYOM calibration measures it live, six AIME problems out of 24 questions.

9Bring your own models

An account can run the router across its own models instead of the built-in tiers. Nine provider types are recognised: Groq, Google AI Studio, OpenAI, Anthropic, Mistral, DeepSeek, Together AI, OpenRouter, and Ollama (the only one needing no key).

The flow: connect a provider → list its models → calibrate them → pick three per chat session. Calibration is stored per (user, model), not per (user, tier), so the same model keeps its measurements whether it sits as cheap in one session and mid in another. The routing map is assembled per session from whichever tiers it was created with.

Provider keys — two options, both honest

modewhere the key livestrade
per-session (default)the browser tab, for that page session; sent with each request, never written to diskrequires no trust in our storage at all; re-enter after a reload
storedencrypted with Fernet (AES) in the database; the key is derived from ROUTER_SECRET_KEY in the environment, never stored alongsideconvenience; a stolen copy of the database alone does not yield the keys

Two deliberate properties of app/storage/key_vault.py: with no server secret set, storing is refused rather than silently downgraded to plaintext — a "we encrypted it" claim we cannot honour is worse than an error saying storage is unavailable. And on secret rotation, decrypt returns None rather than raising, so users are simply asked for the key again.

Only derived numbers — quality, cost, latency — are ever persisted from a calibration run. Never the key, never the prompts.

Does the frontier tier earn its slot?

On everyday questions, no. On competition maths, yes, and the routing policy now acts on that.

Everyday questions can't see a difference. Both paid tiers score 1.000 on the 116-query set: its hard band was labelled against a 3B local model, so it contains things like "write a palindrome check". In a full run the frontier tier was never reached once.

How far to trust it

Ten problems: 7/10 has a 95% interval of roughly 0.40–0.89, so mid sitting under the floor is likely, not certain. The frontier's own accuracy on the band is unmeasured, because it only ran on mid's misses. The run stopped at ten because a frontier AIME answer costs $0.13–0.29 and the balance was low. scripts/probe/run_probe.py --budget makes extending it a bounded spend.

11What didn't work

Four results worth more than the features they replaced.

The embedding scorer (abandoned)

The first FrugalGPT attempt featurised the text of the answer: sentence embeddings of query and answer, their elementwise product and difference, plus lengths. Held-out ROC-AUC 0.66 — at any threshold it rejected right and wrong answers at nearly the same rate. The ablation explained it: embeddings encode topic, not correctness. A right and a wrong explanation of TCP versus UDP have cosine similarity 0.86. Replacing the text features with the model's own confidence took it to 0.80 on the 3B model and 0.735 on the 8B.

DeepSeek R1 as frontier (replaced)

It rescued none of the failures tested, cost 3× the alternative, and averaged 467 seconds per answer. Latency alone disqualifies it from an interactive router regardless of accuracy. It also exposed a real bug: at max_tokens: 16000 it spent 13,697 tokens thinking and returned empty text, which reads downstream as a wrong answer. It had already failed 3 of 12 calibration questions that way, masked by scoring empty as wrong. The cap is now 32,000 — providers bill tokens used, not tokens allowed.

Gemini's free tier (routed around)

Google AI Studio allows 20 requests per day per model, which cannot support a 116-query eval, let alone traffic. The built-in stack reaches the same model through OpenRouter.

Four grading bugs (the most instructive)

Each made a model look worse than it was, and all four were caught by reading answers rather than trusting a score:

the grader wantedthe model saiddamage

Why this is in the documentation

Fixing the multiple-choice bug alone moved the mid tier from 83.2% to 97.5% on the BBH set, and retired a "the frontier rescued this" result that was really mid having been mis-graded — which in turn corrected a published claim of "+4 points for +40% cost" down to +0.7 points for +21% (since recounted as +0.8 for +23% over the 263 distinct questions). The fourth bug, found building the expert set, nearly recorded "mid fails every Countdown puzzle" as the result that justified a frontier band. An automatic grader measures formatting as readily as correctness. Treat every accuracy figure here as a lower bound.

12Limitations

  • The mid-only baseline is a range, not a number — $0.225 from calibration, $0.360 from token repricing. The 41% claim uses the lower one.
  • The classifier is the weakest component. 62% exact-label accuracy on the everyday set, from a k-NN over 176 examples, and 6 of 60 AIME problems are classed as merely hard. Those start at the cheap tier and end at mid, whose answer only gets a structural check. A learned difficulty model trained on the escalation log would do better, and every misroute is either a wasted cheap call or an overpriced answer.
  • hard → cheap is a marginal call. The 8B calibrated at 0.81 against a 0.80 floor on 37 questions; a 120-sample dataset put it at 0.74. The judge caught every wrong hard answer in the measured run, but a weaker judge or a harder distribution would turn that margin into shipped errors.
  • The cheap tier is slower than mid — 6.1s against 3.3s. Cheaper is not faster.
  • The scorer is model-specific. Confidence profiles don't transfer, so a scorer trained for one cheap model is treated as absent for another and the judge runs instead.
  • Paid-tier calibration samples are small — 6–8 questions per band.
  • The expert band rests on ten AIME problems, and the frontier's own accuracy on it is unmeasured. See §10.
  • Auth is project-grade. bcrypt passwords, cookie sessions, per-account and per-device prompt caps — but no CSRF token and no rate limit on login attempts.
  • The escalation cost tail is real. One rate-limit fallback to a frontier tier once cost as much as the other 115 queries combined.

The route trace

Every answer carries the record of how it was routed, built as the cascade runs and finished by the API layer with the routing explanation and the money. It is stored on the chat message (chat_messages.route_trace), returned under _router.trace, and rendered by Why this route? in the chat and reply.explain() in the SDK:

classification
the band; the five nearest labelled questions with their similarity; the similarity-weighted vote; the expert gate's share against its 0.50 bar; any override rule that fired
start
every tier's calibrated score on the band against the 0.80 floor and its expected cost (answer + check + failure-weighted escalation), the tier chosen, and whether direct mode moved it
attempts
each tier tried: model, cost, latency, tokens; what checked it (learned gate with P(correct) and its threshold, the judge's verdict, or the structural check); shipped or escalated
totals
cost, the strongest-tier baseline, saving, and wall time

Python SDK

sdk/python/thriftllm is a thin client over these endpoints. calibrate(model, api_key) returns a calibrated model (reusing a stored calibration unless force=True); Router(cheap=, mid=, frontier=) holds up to three of them and their provider keys in memory; router.chat() posts to /api/v1/route with those keys for that request only. Routing decisions stay on the server: router.route_map asks it rather than recomputing, so the client can never disagree with what routing will do.

15Auth, keys, and quotas

passwords
bcrypt with per-password salt
sessions
httponly cookie, 30-day expiry, Secure when COOKIE_SECURE is set
API keys
rtr_ + 43 random characters; stored as SHA-256, shown once at creation
demo cap
3 prompts per device
account cap
10 prompts per UTC day, across chat and API

API keys are hashed with SHA-256 rather than bcrypt on purpose: they are high-entropy random tokens, not user-chosen secrets. bcrypt's deliberate slowness defends against guessing a weak secret, which does not apply to a 43-character random token — the same reasoning Stripe and GitHub apply to their own issued tokens.

The demo cap is per device, implemented as an id held in both an httponly cookie and localStorage (returned as an X-Demo-Device header), so clearing one leaves the other. Clearing all site data does reset it; that is the limit of what a browser lets a site do without fingerprinting, and the cap exists to bound cost per casual visitor rather than to be unbypassable.

16Persistence

app/storage/connection.py — 272 lines. Chooses the backend; the app's SQL is identical either way.

Local development and a single VM use a SQLite file. A host with no durable disk points at Turso (hosted SQLite) by setting two environment variables.

Embedded replica, not a remote connection

Turso is connected as an embedded replica: a local SQLite file kept in sync with the remote. Writes go to Turso and are durable there; reads are answered from the local copy. That distinction is not cosmetic — measured against the Mumbai region, a remote round trip was ~150ms and a local read ~0.05ms, and one page load makes several queries. 30 message fetches took 2ms through the replica. On boot the replica pulls remote state, so a container that is wiped comes back with every account and chat intact.

Two driver gaps, handled

  • libsql has no sqlite3.Row, so a _Row class reproduces the parts the app uses (lookup by name and index, keys(), in, iteration).
  • It raises a different exception class for duplicate columns, which is why migrations match on the message.
The bug this file exists to prevent

dbconn originally read its environment at import time, and chat_db imports it before anything loads .env — so a correctly configured deployment silently wrote to a local file instead. On a container that means accounts vanish the next time the instance is recycled, presenting exactly as "I signed up, logged in fine, and the next day my login stopped working." It now loads its own configuration, logs the backend at startup, warns when writes won't survive, reports all of it on /health, and re-exposes any variable whose name arrived with stray whitespace — because a deploy console will happily let you type a trailing space into a name field.

17Deployment

A multi-arch python:3.12-slim image. Three things in the Dockerfile are load-bearing:

  • torch from the CPU-only index, installed before the rest of requirements. The default PyPI torch on Linux is the CUDA build — 2–3GB of NVIDIA libraries a CPU host never uses.
  • The embedding model is baked into the image. Otherwise it is fetched from Hugging Face on first use, which on a scale-to-zero host means a 90MB download on every cold start, and an outage if HF is unreachable.
  • Listens on $PORT, one worker. The classifier is ~600MB resident and SQLite wants a single writer; concurrency comes from FastAPI's threadpool inside the process.

Python 3.12 rather than 3.14: prebuilt arm64 wheels for torch and scikit-learn lag the newest Python, and a missing wheel means an hour-long source build that usually fails on a small VM. Note libsql ships no Linux arm64 wheel — x86 hosts install it from a wheel; an ARM box would need a Rust build.

Cold starts

Warm, the deployed service answers in ~90ms. The first request after an idle period is slow for one reason:

steptime (fast laptop; a shared vCPU is slower)
import sentence_transformers4.1s
import litellm2.3s
import torch1.3s
load MiniLM weights5.5s
encode the reference set0.3s
total before the first answer~14s

The app warms the classifier before reporting ready when it detects a serverless host. Those platforms bill by request and throttle CPU outside one, so a background warmup started at boot barely runs until traffic arrives — and then the first visitor waits for the whole load anyway, at throttled speed. Doing it inside the startup phase gets full CPU.

What else helps, in order: turn on startup CPU boost (free); set minimum instances to 1 (removes cold starts, but keeps an instance alive around the clock and will exceed a free allowance); replace torch with ONNX Runtime for the classifier, where ~11 of those 14 seconds live and which would cut resident memory from ~660MB to roughly 200MB. Raising the memory limit does not help — the load is CPU-bound.

Harness lesson

run_probe writes every answer to a JSONL as it arrives and resumes from it. A 12-worker run once tripped the provider's in-flight spend cap at 221 of 298 questions and lost every paid-for result — about a dollar. Concurrency against a low balance is itself a failure mode.
